# Soldeazy 写入链路：架构与验收清单

> 2026-11-07 定稿。用户提出的硬要求：**接口解决、无头运行、改动集不可变、对账可追溯**。
>
> 2026-11-17：整条链路随代码一起搬进独立服务 `soldeazy_mcp_server`
> （入口 `soldeazy-mcp-server`）。工具名、计划文件格式、审计记录、目录布局全部不变，
> 只是不再与 eBay 官方 API 服务同进程、同工具清单。原有计划文件可以直接继续执行。

## 一、一次改动的完整生命周期

```
① 起草  soldeazy_plan_changes(kind, site, targets)
        └ 读当前值（1 次导出）→ 逐条算出 old/new → 写 plan.json（status=draft）

② 确认  soldeazy_confirm_plan(plan_id)
        └ 写 sha256 旁车 + 文件设只读 → 此后任何程序不得修改
        └ 发现要改：另起一份新计划（supersedes 指向旧的），旧计划归档 archive/

③ 执行  soldeazy_apply_plan(plan_id, dry_run=False)
        └ 校验哈希 → 导出（1 次）→ 批量改单元格 → 上传（1 次）
        └ 整个计划 = 2 次请求，与条数无关

④ 对账  soldeazy_reconcile_plan(plan_id)
        └ 轮询导出实际值，与计划的 new 逐条比对
        └ 连续两轮一致即判定稳定；结果写 <plan_id>.reconcile.json
```

## 二、为什么是"导出→批量改→一次上传"

单条保存（打开表单 + 提交）每条要 2 次请求，500 条就是 1000 次；
批量通道固定 2 次请求，规模越大优势越明显。

逐条保存的通道（`apply_datasheet_changes`）已于 2026-11-18 删除——
它从 2026-11-07 起就没有任何调用方，留着只会让"哪个通道是活的"变得含糊。

### 上传与同步是两个动作

| 动作 | 作用对象 | 一次能改什么 |
|---|---|---|
| **上传** | Soldeazy **线下数据表** | E 列（数量）+ F 列（价格）同时写 |
| **同步** | **线上 eBay 刊登** | 勾「价格及邮费」→ `dalign_price=1`；勾「刊登数量」→ `dalign_qty=1` |

**改价和改库存同时生效 = 一次上传 + 同步勾两个键**，不是两条链路。
合并后请求数不变（导出 1 + 上传 1 + 同步 1），工序里也只有一个任务。

`apply_plan` 的同步键**从计划内容推导**（`price_items>0` → 推价格，
`qty_items>0` → 推数量）。旧版默认 `sync_price=True / sync_quantity=False`
对改量计划是错的：会把价格推上去、数量反而不推。

混合计划标 `kind=price_qty`，仅用于历史可读；执行与对账逐条按 `item.field`
取 E 或 F 列，不看 `kind`。

### 平台批量上限：3000 个数据表

导出 / 批量删除 / 同步**共用**一个上限。页面原文：
`(每次批量处理数量上限: 3000)`，JS 注释 `export(max 3000)`。

超过不会报错，只会**静默少做一部分**——这是最危险的失败形态
（工序显示成功，对账才发现一堆"查不到"）。实测某店铺命中 76,096 个数据表，
`whole_result` 只回 3,000 个，漏 96%。

因此：

- `search()` 超过上限时返回 `bulk_limit_exceeded` + 会漏多少条；
- `read_datasheet_values()` **先看数再导**，超限直接报 `SOLDEAZY_RANGE_TOO_LARGE`；
- `apply_plan()` **上传前**检查计划涉及的数据表数，超限中止（"未上传"）；
- 恰好 3,000 不阻断，只留警告（否则这类账号永远改不了）。

**2026-11-18 实机验证**：三道闸全部按预期拦下（真实范围 10,450 > 3,000），
详见 `TODO.md` 的「平台批量上限 3000」一节。同期修掉一个单测覆盖不到的缺陷：
`read_datasheet_values(search=False)`（`reconcile` 走的路）曾让两道闸同时静默失效
——`expected` 恒为 0，可以拿 3,000 条残缺导出当现值。现在由
`search()` 记录 `_last_total_records` 供其沿用。

## 三、对账怎么保证

1. **意图不可变**：计划的 sha256 在确认时锁定，执行前重算，被改过直接拒绝；
2. **冻结与回读必须一致**：`freeze()` 算一次、回读再算一次，两者不符直接
   `SOLDEAZY_PLAN_UNSTABLE` 中止，**一个上传请求都不发**；
3. **读的是线上真相**：对账重新导出，不看接口返回的"成功"字样；
4. **轮询到稳定**：平台应用是异步的，读一次就判会误报（实测出现过 7/8，稍后变 8/8）；
5. **不自动修**：不一致只报告，由人决定是补一份新计划还是接受现状；
6. **留痕**：`<plan>.audit.jsonl` 记录每次执行，`<plan>.reconcile.json` 记录每次对账。

## 四、运行形态

| 项 | 值 | 说明 |
|---|---|---|
| 浏览器 | **无头**（`SOLDEAZY_HEADLESS` 默认 1） | 只在首次登录或需要人工介入时开有头 |
| 进程 | 单例常驻 | MCP 服务端全程一个浏览器，不重复登录 |
| 登录 | 勾「记住用户名」+ cookie 落盘 | `session_cookies.json` 保存含会话级的 cookie，重启可复用 |
| 导出通道 | 纯 cookie（`export_via_api`） | 页面表单通道已于 2026-11-17 删除：它在部分会话下弹层不出现（FUN 实机复现），cookie 通道实测一次拿全 7,075 行且与页面通道逐格一致 |

## 六、已知限制

- 批量通道失败粒度整份，不像逐条那样能精确到某一条；
  对账会补上这个信息（哪几行没生效）。
- 多变体数据表的子体行变更走"母体 SKU 展开"，用户的输入必须是母体 SKU。
- 价格只按子体 SKU 精确匹配；前缀命中多条时报冲突，不猜。
